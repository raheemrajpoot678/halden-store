## Commands

```bash
npm run dev          # Next.js dev server (Turbopack) on http://localhost:3000
npm run build        # Production build
npm run lint         # ESLint (flat config, eslint-config-next)
npx tsc --noEmit     # Typecheck

npm run db:generate  # drizzle-kit: generate SQL migrations into ./drizzle
npm run db:migrate   # drizzle-kit: apply migrations
npm run db:push      # drizzle-kit: push schema directly (no migration files) — don't use; see Database conventions
npm run db:studio    # drizzle-kit: Drizzle Studio
npm run db:seed      # tsx: upsert the sample catalogue + demo accounts (src/db/seed.ts), safe to re-run

npx auth@latest generate --config src/lib/auth.ts --output <scratch file>   # Better Auth table definitions to merge into src/db/schema.ts
```

No test runner is configured yet.

## Stack

Next.js 16 (App Router, `src/` dir, `@/*` → `src/*`), React 19, TypeScript, Tailwind CSS v4 (configured via `@tailwindcss/postcss` and `src/app/globals.css`, no `tailwind.config`), Better Auth, Drizzle ORM, Neon Postgres.

## Architecture

- **Database** — `src/db/index.ts` exports a single `db` built with `drizzle-orm/neon-http` over `@neondatabase/serverless` (HTTP driver, stateless, no pooled connections or interactive transactions). It throws at import time if `DATABASE_URL` is unset, so any module that imports `@/db` (including `@/lib/auth`) needs the env var present, even during `next build`.
- **Schema** — `src/db/schema.ts` is the single schema file. It is passed both to the Drizzle client (for the relational query API) and to Better Auth's Drizzle adapter, and `drizzle.config.ts` points drizzle-kit at it. It also holds Better Auth's `user` / `session` / `account` / `verification` tables (see Auth).
- **Auth** — `src/lib/auth.ts` is the server-side Better Auth instance (Drizzle adapter, `provider: "pg"`, email + password, the `admin` plugin for roles/bans, and `nextCookies()` last so Server Actions can set cookies). It is mounted by the catch-all route `src/app/api/auth/[...all]/route.ts` via `toNextJsHandler`. `src/lib/auth-client.ts` is the React client (`authClient`, with `adminClient`) for client components, pointed at `NEXT_PUBLIC_APP_URL`. Server code should import `auth` from `@/lib/auth`; client code must only import `@/lib/auth-client`.
  - Routes: `/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`, `/account`, `/admin` (role `admin` only, else 404). Server pages read the session through `src/lib/session.ts` (`getSession`, `requireSession`, `isAdmin`, `requireAdmin`, `getAdminSession`, `safeRedirectPath`); this makes them dynamic, so never call it from the header or other ISR pages.
  - There is no email provider: `sendResetPassword` goes to `src/lib/dev-mailbox.ts`, which logs the link and, outside production, shows it on `/forgot-password`. Wire a real provider in there before launch.
  - Demo accounts live in `src/lib/demo-accounts.ts`, are (re)created by `db:seed`, and are listed on `/sign-in` outside production or with `NEXT_PUBLIC_SHOW_DEMO_ACCOUNTS=true`.
  - Auth tables are hand-merged into `src/db/schema.ts` (timezone-aware `timestamps`, `role`/`banned` not null). After adding a plugin, run the CLI generate to a scratch file, merge the new columns, then `db:generate` → `db:migrate`.
- **Cart ("bag")** — tables `carts` (one per user via unique `user_id`, or per guest via the httpOnly `halden_cart` cookie whose value is the cart id) and `cart_items` (unique per cart + product, `quantity > 0`). Prices and stock are always read live from `products`; never store them on cart rows. Reads and writes live in `src/lib/cart.ts` (single conditional statements, quantities capped by stock and `MAX_PER_LINE` from `src/lib/cart-config.ts`); components call the Server Actions in `src/app/(store)/bag/actions.ts`, which return the updated `Cart`. `CartProvider` (`src/components/cart/`) applies every change optimistically with `useOptimistic` (reducer mirrors the server caps via the shared `toCartLine` / `toCart` in `cart-config.ts`), then swaps in the `Cart` the action returns; a rejected or failed action rolls back to the last server state and returns an error. Controls therefore never disable while a request is pending. The header badge and `MiniBag` drawer load via `GET /api/cart`, so the ISR pages that render the header never read cookies — don't call `getCart` from the header, layout or ISR pages. A Better Auth `hooks.after` in `src/lib/auth.ts` merges the guest cart into the user's on sign-in/sign-up (`src/lib/cart-merge.ts`) and clears the cookie; auth UI calls `useCart().refresh()` afterwards. Sold-out lines stay in the bag but are excluded from totals and flag `hasIssues`. Abandoned guest carts are not cleaned up yet.
- **Checkout (Stripe)** — Stripe-hosted Checkout Sessions, one-time payments in USD. The bag's form action `checkout` (`src/app/(store)/bag/actions.ts`) calls `startCheckout` in `src/lib/checkout.ts`: it cancels the cart's older open checkouts, **reserves stock** (`reserveStock`, all-or-nothing), inserts a `pending` row in `orders` (line snapshot in jsonb `items`), creates the session (`metadata.orderId`, 30-minute `expires_at`, free shipping rate, allowed countries in `src/lib/checkout-config.ts`) and redirects to it. Never pass `payment_method_types` (dynamic payment methods) and don't enable `automatic_tax` without a tax registration. The signature-verified webhook `src/app/api/stripe/webhook/route.ts` drives fulfilment: `checkout.session.completed` / `async_payment_succeeded` → `markOrderPaid` (or `processing` while unpaid), which also removes the bought pieces from the bag; `async_payment_failed` / `expired` → `releaseOrder`, which returns the stock; `refund.created` / `refund.updated` / `charge.refunded` → `syncRefund` and `charge.succeeded` / `charge.updated` → `recordStripeFee` (both in `src/lib/refunds.ts`) — enable these events on the Stripe endpoint. All order transitions in `src/lib/orders.ts` are single status-guarded statements, so retries are no-ops; `/checkout/success` also calls `markOrderPaid` so it never shows a paid order as pending, and `/checkout/cancel` (the `cancel_url`) expires the session immediately. While a checkout is `pending`, `loadCartLines` adds the cart's own reserved stock back so its bag still reads as available, and editing the bag cancels the open checkout. Stripe access goes through `getStripe()` in `src/lib/stripe.ts` (lazy, so builds don't need keys). Local webhooks: `stripe listen --forward-to localhost:3000/api/stripe/webhook`.
- **Admin dashboard** — `src/app/admin/` has its own shell (`layout.tsx`: sidebar `AdminNav`, `NotificationBell` polling `GET /api/admin/notifications/count`). Every page calls `requireAdmin` and every Server Action `requireAdminAction` (`src/lib/admin/authorize.ts`); the layout check alone isn't a security boundary. Admin data access lives in `src/lib/admin/` (`catalog`, `orders`, `customers`, `analytics`, `payouts`, `validation`, `params`, `shared`), shared UI in `src/components/admin/` (`ui.tsx` for page header / panels / badges / tables / pagination; forms use `useFormAction`, which avoids React's automatic form reset so input survives validation errors). Catalogue edits call `revalidateStorefront` for the ISR pages. Products are archived, never deleted; editing a product never writes `stock` (it goes through the conditional `adjustStock`). Orders: payment `status` adds `partially_refunded` / `refunded` (captured = `PAID_ORDER_STATUSES`), and a separate `fulfilment_status` (`unfulfilled → shipped → delivered`, with carrier/tracking shown on `/account`). Refunds are issued from the order page via `issueRefund` (Stripe Refund API, idempotency key per refund state), recorded in `refunds`, and `orders.refunded_cents` is always recomputed from those rows; optional restock is claimed once per refund. `notifications` is a shared admin feed written only when a guarded transition actually changed a row (paid, processing, failed, refund, low stock). Revenue: gross counted at `paid_at`, refunds at issue date, net = gross − refunds − `stripe_fee_cents` (converted from the Stripe account's settlement currency to the order's). Payouts and balance are read live from Stripe (settlement currency). `db:seed` adds sample orders with fixed hashed ids and no Stripe ids.
- **Design system** — everything lives in `src/app/globals.css` (Tailwind v4 `@theme` tokens plus `@utility` primitives; there is no `tailwind.config`). The default Tailwind color palette is removed (`--color-*: initial`), so use the semantic colors (`canvas`, `surface`, `ink`, `ink-muted`, `ink-subtle`, `line`, `accent`, `sale`, `success`), the type scale (`text-caption` … `text-display`), and the primitives (`container-page/content/prose`, `section`, `grid-products`, `rail`, `media-frame`, `btn` + `btn-primary/secondary/light/sm/block`, `field` + `field-label` (form inputs), `link`, `link-quiet`, `link-cta`, `eyebrow`, `ui-label`, `hairline`, `theme-inverse`) instead of ad-hoc values. Corners are square; there is no automatic dark mode — dark sections use `theme-inverse`.
- **Storefront** — storefront routes live in the `src/app/(store)/` route group, whose layout renders `StoreChrome` (`SiteHeader` / `SiteFooter` / `MiniBag`); the root layout only holds `<html>` and `CartProvider`, and the root `not-found.tsx` brings its own `StoreChrome`. Only `products.status = 'active'` is listed: every query in `src/lib/products.ts` adds `isActive` itself (a later `.where()` replaces an earlier one), and the cart treats draft/archived pieces as sold out; homepage sections live in `src/components/home/`. Stock state (in stock / low stock ≤ 3 / sold out) comes from `getStockStatus` in `src/lib/stock.ts` and is shared by the PDP and `ProductCard`. Sample photos must not show readable brand names or logos — check them at full size, not thumbnails. Unsplash photos must be rendered with `UnsplashImage` (`src/components/unsplash-image.tsx`), which resizes via Unsplash's CDN; plain `next/image` with Unsplash URLs is not allowed by `next.config.ts` and would time out in the built-in optimizer anyway.
- **Database conventions**
  - Schema changes go through versioned migrations: `db:generate`, review the SQL, commit `./drizzle`, then `db:migrate`. Never `db:push`.
  - Money is stored as integer cents (`*_cents` columns); `formatPrice` takes cents. Never store or pass prices as floats.
  - Until product variants exist, stock is the single `products.stock` integer (≥ 0). Decrement it with one conditional `UPDATE … SET stock = stock - n WHERE stock >= n`, since the neon-http driver has no interactive transactions.
  - Data that is only ever read with its parent row (product `details`, `images`) lives in `text[]`/jsonb columns, not child tables, until something needs to query it independently.
  - Components never import `@/db`. Storefront reads go through `src/lib/products.ts`, with each query wrapped in React `cache`. Homepage curation stays as slug lists in `src/lib/catalog.ts` until collections are modelled.
  - DB-backed storefront pages use ISR (`export const revalidate = 60`) and keep the default `dynamicParams`, so new products render on demand. `next build` therefore needs a migrated and seeded database.
  - `src/db/seed.ts` must stay idempotent: upsert on slug, never plain insert.
- **Env** — see `.env.example`: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`. `drizzle.config.ts` and `src/db/seed.ts` load `.env.local` then `.env` via `src/db/load-env.ts` (import it first in any new script that touches `@/db`); Next.js loads them itself.
